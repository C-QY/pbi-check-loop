# pbi-check-loop

> **Power BI Desktop 没有「重新读取磁盘上已改动的 PBIP」这个功能——产品里根本没有这条命令。**
> 这个项目把它补上，再加上一条让 agent 看见渲染结果的通道，
> 使 AI 辅助的 Power BI 开发从「每轮都要停下来等人」变成一个闭合的回路。

**[English →](README.md)** · 仅 Windows · PowerShell 5.1+

---

## ✨ 它做什么

🔁 **agent 能修自己犯的错** —— 写 TMDL、重载、把报错当文本读出来、改对、再来一轮  
🚦 **先查再重载** —— 盘上没变就不重载，白重载一次要赔上一次完整的模型加载  
👀 **两条观察通道** —— 有视觉的模型看 PNG，没有的走 UI Automation 读文字  
🪟 **窗口放回原处** —— 原显示器、原位置；启动时若弹登录框，顺手关掉  
🤝 **多 agent 安全** —— 按项目名认自己的实例，绝不误杀别人的 Desktop

## 全局视角：AI 工作流断在哪

PBIP 格式是前提——是把 PBI 当做**项目文件**进行版本控制、团队协同开发的技术，
实现**模型层（M 和 DAX）与报表层（Prototype 和 Visual Implement）分离**的基础。
有了它，agent 才谈得上直接操作报表。

在此之上，AI 辅助的 Power BI 开发其实是四件成熟度完全不同的事：

| 层 | 要做的事 | 谁来验证 | 闭环状态 |
|---|---|---|---|
| **结构** | TMDL/PBIR 合不合法？字段绑没绑上、视觉对象在不在画布内？ | 把文件读回来 | ✅ 早就可自动化 |
| **数值** | 这个度量算出来对不对？ | ADOMD/DAX 连实时模型对账 | ✅ **早已是高保真闭环** |
| **刷新** | Desktop 到底有没有*看见*磁盘上写下的东西？ | — | ❌ **产品里没有这个功能** |
| **视觉** | 渲染出来的页面跟原型图一致吗？ | — | ❌ **每一次都得靠人** |

**模型层早就有一个高保真的闭合循环。** ADOMD 连本地 Analysis Services 实例，跑 DAX，
把数字跟源头对上。agent 写完度量、查一次、就知道对不对，不需要人。

**缺的是文件写下去之后的所有环节。** 而它断在两个地方。

### 一、Power BI Desktop 没有「从磁盘重新载入」

把话说明白：**Power BI Desktop 没有提供任何方式，去重新读取磁盘上已经变化的 PBIP 项目。**
文件 → 保存，是把内存写到磁盘。反方向的命令，产品里哪儿都找不到。

同步是单向的，而且方向恰好是错的：

| 方向 | 命令 | 有吗 |
|---|---|---|
| 内存 → 磁盘 | 文件 → 保存 | ✅ |
| **磁盘 → 内存** | **—** | ❌ **没有** |

在人手敲每一条度量的年代，这个不对称无伤大雅：内存永远是更新的那一份。
可一旦 agent 直接写 TMDL，它就变成了核心障碍——因为**现在磁盘才是新的那一份，
而你没办法告诉 Desktop。** 更糟的是，仅有的那条同步命令还会主动毁掉成果：
此时按 <kbd>Ctrl</kbd>+<kbd>S</kbd>，**旧的内存模型会把新的磁盘内容覆盖掉**。

所以工作流里"自然语言"的那一半其实已经跑通了：你把需求说出来，agent 把语义模型改在磁盘上，
改得也对。然后它就卡死在这里——因为没有任何受支持的办法让运行中的 Desktop 看到它。
唯一的出路是人手动关掉再打开，每一轮迭代都要来一次。

**这就是本项目补上的空缺。** `pbi-reload.ps1` 提供那个缺失的「磁盘 → 内存」方向：
结束进程且不保存（所以旧模型永远赢不了）、清理残留的 `msmdsrv`、
用同一个版本重新打开同一个项目，并把窗口放回原处。

机制上要说准确：**这是重启，不是热重载。** 窗口确实关了，
变的只是「关掉再打开」不再是人的活。每一轮仍然要赔一次完整的模型加载，
那也依旧是每轮迭代最大的开销。

#### 另一条路：直接写进运行中的模型

确实有办法不重启就改动运行中的模型：**TOM 连本地 Analysis Services 实例**，直接写模型元数据——
整个外部工具生态都建立在这上面。它**确实更快**，但值得把它覆盖到哪、覆盖不到哪说清楚：

| | TOM 热写入 | 效果 |
|---|---|---|
| **DAX 度量** | ✅ | **完全生效**——度量是查询时求值的，下一次查询就用新定义 |
| **Power Query / M** | ⚠️ | 定义变了，但**已加载的数据不会自己重新物化**，要触发 refresh 才变 |
| **报表层**（PBIR、`visual.json`） | ❌ | **根本没有热写入 API**——布局和视觉对象只是文件，永远只是文件 |

所以热写入是真的可行，纯 DAX 的活它更快。**这个项目仍然选慢的那条路，原因是版本控制。**

TOM 写的是一个运行中进程的内存。**在有人按保存之前，磁盘上什么都没有**：
没有 diff 可看、没有 commit 可回滚、没有分支、没有 PR。
严格说不是"完全无法版本控制"，而是**版本控制从「媒介」退化成了「事后补记」**——
先热写、再保存、再提交，而中间那步保存是 Desktop 里的手动动作。
两个人同时热写同一个实例，更是最后写的赢，连冲突都不会报。

这就是真实的取舍。每轮赔一次完整模型加载，换来的是**每一次改动在生效之前，
都是一份可评审的文本 diff**——而且报表层（它压根没有热写入这条路）
能跟模型层用同一套工作流，不用维护两套。

### 二、报表层的产物是像素，不是文件

agent 能写 `visual.json`，却看不见它渲染成什么样——对没对、错没错位，一概不知。

两件事加起来，净效果就是：**人成了 agent 的眼睛和手。** 这不是习惯问题，是这个回路结构上就是开的。

> **有观测 ≠ 有闭环。** 截得到图，不等于会判断——那等于有 stdout 但没有 assert。
> 闭环需要判据。见 [Loop 2](#loop-2--报表层照着原型图迭代)。

## Loop 1 —— 模型层：改、重载、诊断、再来

这是语义模型工作的回路：加度量、改关系、重构 M。
你用自然语言描述需求，agent 把 TMDL 改在磁盘上——
然后 **Reload 提供了 Power BI 自己没有的那一步**，让运行中的 Desktop 读到它。

```
       ┌─────────────────────────────────────────────────┐
       │                                                 │
   改磁盘上   ──▶ Check ──▶ Reload ──▶ 加载 ──▶ 报错？ ───┤
   的 TMDL       │           │                  │        │
                 │           │                  ▼        │
             「没变？」    人确认过           Shot -Text  │
              到此为止      给 -Yes           读出来 ─────┘
```

**每一块各管什么：**

- **Check** 回答*磁盘上到底变没变*。没变就停——白重载一次要赔上一次完整的模型加载
- **Reload** 让 Desktop 重新读盘。这就是过去每一轮都得手动来一次的那一步
- **Shot `-Text`** 把报错弹窗**当文本读**，而不是当像素认。
  一个能逐字读到 `The column 'Amount' of the table wasn't found` 的 agent，
  通常能自己改对，然后自己再跑一轮

最后这点，是把"处理报错"从打断变成回路的一部分。
从图片上认错误是猜，把它当字符串读到才是诊断。

> ⚠️ **数值仍然归 ADOMD 管。** 这个 skill 只告诉你模型*加载成功了*，
> 不告诉你度量*算得对*。那件事要连实时模型跑 DAX——那个闭环本来就有，这个不替代它。

**重载不是刷新数据——而这正是关键。** 重开会重新读取模型定义、并用缓存数据把所有 DAX 重算一遍，
这恰好就是改度量、改关系、改格式所需要的全部。它不回源：

| 改了什么 | 需要什么 |
|---|---|
| 度量、关系、格式、PBIR | 重载即可，秒级 |
| 源表里的数据行 | 手动点 Refresh——分钟级，而且是人的决定 |
| **分区的 M 表达式**（加列、改查询、加表） | **两件都要。** 重载会让该表的缓存数据作废——它会变成**空表**，所有 M 里引用它的表也跟着变空，绑在上面的页面渲染成空白。这是预期行为，不是改坏了 |

这个区分对闭环很重要。每轮都刷新会把秒级变成分钟级，还可能真的去连生产库，
所以 skill 里明确禁止 agent 触发刷新。**改"怎么算"是迭代；改"算哪批数据"是新任务，也是人的决定。**

第三行是最容易误判的一条，所以 skill 里把症状写明白了：改完 M 之后，绑在那张表上的页面会渲染成
空白，看起来和"改坏了"一模一样。要让 agent 认得出这个症状、主动说明，并把 Refresh 交还给用户，
而不是闷头以为自己搞砸了。

### 等模型加载完

大模型打开要几十秒，**在它加载完之前，下游任何动作都不作数**——对着半加载的模型跑 DAX，
要么报错要么给你假数据。`-Wait` 会阻塞到就绪为止：

```
Waiting for the model to finish loading (timeout 180s)...
Ready after 23s - title settled and the model engine is up.
  Analysis Services: localhost:58894   [msmdsrv 29412]
```

它存在的原因是：**最直觉的那种轮询写法是坏的**。"等到标题不再是 `Untitled - Power BI Desktop`"
在中文版 Desktop 上直接失效——中文显示的是「无标题」，于是这个判断在任何窗口一出现就通过了，
调用方随即去查一个还在加载的模型。`-Wait` 改成匹配**项目名**：只有加载完成才会产生它，且不分语言。
这和这个工具存在的理由是同一个——朴素版本的检查，恰恰是会静默报成功的那个。

后来发现**光看标题也不够**：标题会在模型引擎还没起来时就变成项目名，那一刻发出的 DAX 查询会
返回「找不到表」——和"改动把模型搞坏了"完全无法区分。所以现在 `Ready` 同时意味着两件事：
窗口标题稳定了，**且**该实例的 `msmdsrv` 已经起来。

### 找到该连哪个实例

就绪后，`-Wait`（以及 `-ListOnly`）会直接打印端点：

```
AS        localhost:58894
```

这补上了闭环缺的最后一段。**截图只能证明视觉对象「渲染出来了」，只有 DAX 查询能证明数字「是对的」**，
那就得有人告诉 agent 该把查询发到哪里。

最直觉的来源——工作区目录里的 `msmdsrv.port.txt`——在开着多个项目时是个陷阱：最新的那个端口文件
属于最后加载的项目，于是 agent 可能连到**另一个项目的模型**上，去查一张只存在于它正在改的项目里的表，
得到「找不到表」。这看起来完全像是改动出了问题，会把排查引向完全错误的方向。
而「父进程 PID → 子 msmdsrv → 监听端口」这条链没有歧义，所以工具直接替你解析好。

### 两类报错，处理方式相反

刚改完就重新打开，恰恰是最容易出问题的时刻——而第一步是分类，因为这两类要的处理正好相反。

| | **A 类 —— 文件打不开** | **B 类 —— 某张视觉对象坏了** |
|---|---|---|
| 症状 | 弹模态框，项目根本没加载 | 报表渲染出来了，只有某一张报错或空白 |
| 闭环状态 | **断了** —— 后面一步都跑不了 | **仍然通** —— Reload 和 Shot 都还能用 |
| 处理 | 读报错 → **关掉这个实例** → 修盘上文件 → 重新打开 | 原地诊断，**不要关** |
| 为什么 | 坏进程占着项目、`msmdsrv` 子进程也赖着，下次重载要跟这两样打架 | 关掉等于白白丢掉一个还能用的闭环 |

A 类通常是 TMDL 语法错、引用了已经不存在的东西、或者关系非法。
B 类通常是 `queryRef` 指向了改过名的度量，或者某一张表静默加载失败而其他部分正常渲染。

> ⚠️ **不是每个改坏的地方都会弹框。** 实测确认：一个写坏的计算表会让项目正常打开、然后静默失败。
> 没有报错框，不等于改对了——要去确认你改的那个东西真的渲染出来了。

## Loop 2 —— 报表层：照着原型图迭代

这是过去完全敞开的一段，也是这个项目存在的原因。

**原型图不是美工产物，它是判据（test oracle）。**

agent 回答不了*「这看起来对吗」*——那个问题没有它够得着的基准。
但它回答得了*「这跟原型图一致吗」*——而这个问题，从一张图上就能判定。
给出原型图，等于把一个无解的问题换成了一个可解的问题。

```
   原型图（判据）
        │
        ▼
   写 PBIR ──▶ Reload ──▶ Shot（PNG）──▶ 与原型图比对
        ▲                                     │
        │                                     ▼
        └────── 还差？调整 ◀────────── 一致？收工
```

于是工作流变成：**先跟人一起把原型定下来，然后让 agent 无人值守地收敛过去。**
人定靶子，agent 跑圈。

`SKILL.md` 里把它写成了一份 agent 逐条执行的清单，所以这个闭环是**流程**，不是建议：

```
- [ ] 0. 确立判据 —— 原型图，或一份写清楚「什么算对」的说明
- [ ] 1. 确认没有未保存的改动（开头问一次，不是每轮都问）
- [ ] 2. 改磁盘上的 PBIR/TMDL
- [ ] 3. Reload
- [ ] 4. 等标题稳定，然后 Shot
- [ ] 5. 与判据比对，列出具体差异
- [ ] 6. 还有差异且轮次 < 2 → 回第 2 步；否则停下汇报
```

三条规则守住这件事的诚实性：

- **没有判据就不跑这个闭环。** 没有原型图时，agent 只跑一轮、把结果给你看、由你来判。
  绝不许自己编一个标准、再宣布达标了
- **未保存改动只在开头问一次，不是每轮问。** 每轮都重新确认，就等于放弃了「无人值守」这件事本身——
  但如果你中途动了 Desktop，闭环会停下来重新问
- **两轮不收敛就停。** 每一轮都要赔一次完整的模型加载，而第三轮很少能找到前两轮没找到的东西

## agent 会自己想起来用它

一个"等着被调用"的工具，结构上就把人留在了回路里。所以 skill 里明确要求 agent 主动执行，
并按**每个动作能毁掉什么**分级：

| 动作 | 风险 | 行为 |
|---|---|---|
| **Check** | 无——纯只读 | 写完任何项目文件**立即执行**，从不询问 |
| **Shot** | 无——纯只读 | 需要看结果时随时执行，从不询问 |
| **Reload** | 高——杀进程且不保存 | **每会话授权一次**，此后先说后做 |

这两半都写在 skill 的 `description` 里——那是每个会话都会预加载的部分——而不只是写在正文。
**一条"自主行动"的指令被预加载，而它的安全前提要等到正文加载后才出现，那就等于一条"不安全行动"的指令。**

### 怎么保证它真的被用起来

skill 装上以后，靠**描述与你的话做语义匹配**才会被选中。而这正是薄弱点：当你说
*"把这个度量改成排除统购"*，这句话里**没有任何词提到重载或 Desktop**。
agent 完全可能改完就认为任务结束了——改动躺在磁盘上，谁也看不见。

所以这份 description 是围绕**"是不是在动一个 `.pbip` 项目"**写的，而不是围绕"重载"这个词，
并且明确写着：**重载没跑，这次修改就不算完成。**

对于天天要动的项目，把它变成一条常驻规矩。仓库 `CLAUDE.md` 里的一行，比 description 怎么措辞都可靠：

```markdown
改完任何 .tmdl / .pbir / visual.json 后，先用 pbi-check-loop 重载再汇报完成。
磁盘改了而 Desktop 没重读，就等于没改完。
```

用 `PostToolUse` hook 也能机制性地强制执行，但它每次编辑都会触发——包括跟 Power BI 毫无关系的文件——
而且完全剥夺了 agent 的判断。常驻规矩能拿到绝大部分可靠性，却不用付这些代价。

Reload 的不对称很关键：**每次都问**等于把人重新塞回内环——那正是这个项目要消除的成本；
**从不问**则是在拿未保存的工作打赌。所以授权只取一次，在开头：

> 我要重载 Desktop 验证一下，之后每次改完也会这么做。这会丢弃 Desktop 里未保存的改动——
> 期间请不要在 Desktop 里手动编辑，可以吗？

拿到之后，agent **先说一句再执行，不等回应**——一行说明，然后重载。它不会每轮阻塞等你点头，
但也不会一声不吭：重载会让 Desktop 黑屏十几秒，静默会被误认为卡死。
前提被打破时重新确认——你说自己动了 Desktop、你接管了窗口、或者你喊停。

## 哪些环节刻意留给人

有些环节是故意不闭的。不是因为工具不成熟——是因为闭上它才是错的：

- **「Desktop 里有没有未保存的改动？」**——存在两种方向相反的情况，
  而工具**从外部分辨不了**：

  | 情况 | 正确做法 |
  |---|---|
  | 磁盘 TMDL 已被改，Desktop 内存是旧的 | 绝不能保存——会覆盖磁盘 |
  | 有人刚在 Desktop 里改了还没存 | 必须先保存——否则杀掉就没了 |

  Desktop 的标题栏不带修改标记，枚举窗口也拿不到脏状态。
  **这是信息不对称，不是能力不足。** 所以脚本没有 `-Yes` 就拒绝动手，
  而这个确认发生在对话里——绝不弹窗

- **业务口径。** "收入"含不含关联交易，这不是一张截图能定的
- **品味的最后一公里。** agent 能收敛到原型图；判断这张原型图对不对，是你的事

## 三个模式

| 模式 | 做什么 | 命令 | 无视觉可用 |
|---|---|---|---|
| **Check** | 盘上文件是否比运行中的实例新？报告 PID、版本、标题 | `pbi-reload.ps1 -ListOnly` | ✅ |
| **Reload** | 结束进程、清理 `msmdsrv`、用同版本重开、还原窗口 | `pbi-reload.ps1 -Yes` | ✅ |
| **Shot** | 窗口截成 PNG，或 `-Text` 走 UI Automation 读文字 | `pbi-shot.ps1` | ✅ 用 `-Text` |

`-Text` 不是降级方案。它能读到对话框文字、表/字段树，以及**报表画布本身**——视觉对象标题、
矩阵列头、单元格数值，都从内嵌 WebView 的无障碍树里暴露出来。它在精确字符串上往往**比图片更准**：
截图里被截断成 `SALES_DETAIL_BY_RE…` 的名字，文本里是完整的。真正的边界是**语义 vs 呈现**：
文本告诉你报表*说了什么*，只有图片能告诉你它*长什么样*。

> ⚠️ **只有图片模式需要视觉能力。** 纯文本模型调了图片模式再去描述报表，就是在编造内容——
> 那比没有截图更糟。skill 里明确要求这类模型改用 `-Text`，或者把路径交给人看。

## 它不做什么

- **不会让加载变快**。Desktop 的模型加载一秒没省，而那才是每轮迭代的耗时大头
- **agent 不能操作报表**——不能滚动、点击、切页。问题不在当前屏幕上，就得人先导航过去
- **不核对数值。** 那是 ADOMD 的活，而那个闭环本来就有
- 它闭合的是报表层的「看见」，不是「判断」——判断需要判据

## 和 Power BI Desktop Bridge 的关系

Power BI Desktop 在 2026 年 6 月发布了 **Desktop Bridge** —— 预览版，要求 Desktop `2.155.756.0`
及以上，且位于 Preview Features 开关下。它是跑在 Desktop 进程内的本地 JSON-RPC 服务，一共四个
方法：`bridge.manifest`、`application.state.get/v1`、`file.reload/v1`、`report.snapshot.capture/v1`。

其中两个和本项目直接重合，**重合的部分，优先用 Bridge。** 它的 reload 是进程内完成的 —— 不重启、
不重新加载模型，有未保存改动也不会被抹掉；它的截图是内部渲染报表，不是抓窗口。两样都比从外面驱动
Desktop 干净，而从外面驱动正是这两个脚本在做的事。

这四个方法没覆盖的：

- **覆盖面。** Bridge 要求较新的 build 加一个预览开关。企业统管的安装不会更新得那么快，而
  Power BI Report Server 版 Desktop 是另一条产品线，我没有找到任何迹象表明 Bridge 在那里存在。
  PowerShell 脚本则装的是哪个版本就跑哪个版本。
- **报错。** `application.state.get/v1` 只返回 `currentFilePath` 和 `hasUnsavedChanges`，没有别的。
  Desktop 拒绝加载一个文件时，没有任何方法、追踪日志、stderr 或事件日志会说明这件事
  （[microsoft/skills-for-fabric#40](https://github.com/microsoft/skills-for-fabric/issues/40)）——
  报错只以屏幕上一个对话框的形式存在。去刮那个对话框的文字很粗糙，但一个分不清「加载成功」和
  「被拒绝」的 agent，没法从自己的错误里恢复，而那正是 Loop 1 的全部意义。
- **模型。** 没有端口，也没有查询入口。截图能证明报表**渲染出来了**，证明不了数字**是对的**。
  `pbi-reload -Wait` 会打印 Analysis Services 端口，好让 ADOMD 客户端去核对；而且它是按进程血缘
  解析这个端口的，不读 `msmdsrv.port.txt` —— 后者在同时打开两个项目时会静默指向另一个项目。

**我没有实测过 Bridge。** 本机的 build 是 `2.150.2455.0`，低于它的门槛，所以上面这些都是读文档和
别人的记录得来的，不是我自己跑出来的。欢迎指正。

## 设计原则

**快速 · 轻量 · 通用** —— 脚本只采集元数据，从不读取文件内容。

| 层 | 内容 | Token 成本 |
|---|---|---|
| L1 | `SKILL.md` frontmatter | 每个会话约 285 tokens，用不用都付 |
| L2 | `SKILL.md` 正文 | 约 5600 tokens，触发后才加载 |
| L3 | `scripts/*.ps1` | 执行而非读取，零 token |

---

## 它到底是什么

用最窄、也最诚实的说法：**它自动化的是「agent 改完文件」到「agent 能看见改动的效果」这一段。**

这个定位刻意做小，而这正是两个简单脚本就够用的原因。缺口本来就不宽——改，早就能改；判断，早就能判断。
**只有中间那一小段是空的，而它恰好卡在每一轮迭代的必经之路上。**

落到实处只有一句话：**改 TMDL 的 agent，现在能从自己犯的错里爬起来了。**
写度量 → 重载 → 把报错当文本读出来 → 改对 → 再来一轮，全程不需要人转述屏幕上写了什么。
其余所有东西，都是为这一件事服务的。

### 一个猜想，就当猜想看

这个形状也许不止 Power BI 有。一个把状态存在内存而非磁盘、产出是像素而非文件、
并且假设「编辑发生在应用内部」的 GUI 工具，一旦 agent 开始从外部改它的文件，
大概会卡在同一个地方。补法估计也是那两招——把状态刷新机械化，开一条观察通道。

**但这是从单个案例推出来的猜想。** Power BI 是我真正趟过一遍的那一个，
Figma、Unity 之类我一个都没验证过。**当成一个值得去测的假设，别当成结论。**

## 一句实话

这两个脚本加起来几百行 PowerShell，**没有任何精妙代码**。时间全花在那些实证上——
登录弹窗延迟 11 秒才出现、守候进程必须独立否则随会话一起死、`IsZoomed` 对一个根本没被撑开的
窗口返回 `True`。**任何人重做一遍，都会撞上同样的墙。**

价值在 [`docs/FINDINGS.md`](docs/FINDINGS.md) 里那些实证，不在代码。
